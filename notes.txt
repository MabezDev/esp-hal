1. WHAT THIS REVIEW CHANGED
---------------------------

Reviewed the three flash design documents, fact-checked every citation against
the actual source, and edited all three.

  a) Detection provenance. Originally attributed the cached JEDEC ID to the
     first-stage ROM. I first concluded that was wrong and that only the
     second-stage bootloader wrote it. Scott pushed back (the ROM must configure
     flash to load the second stage) and he was right - see section 2. Final
     position is in FLASH-DESIGN.md "Where the cached ID comes from" + appendix B2.

  b) Byte order bug. The cached `device_id` is manufacturer-first (bits 23:16),
     but the esptool table and esp-storage's decoder both read the RAW RDID order
     (manufacturer in bits 7:0). Porting the table verbatim mis-decodes capacity
     on every board. Confirmed four independent ways - see section 3.

  c) Chunk size. Design used 256 bytes everywhere: 16x smaller than esp-storage
     (which chunks by SECTOR_SIZE 4096, NOT "sector or page" as the old appendix
     C2 claimed) and 32-64x smaller than ESP-IDF's MAX_WRITE_CHUNK 8192 /
     MAX_READ_CHUNK 16384. Now split so the bounce buffer bounds only the staged
     path. FINAL (D1, Scott): direct = ESP-IDF's ceilings, 16384 read / 8192
     write; staged = the bounce buffer's size.

  d) Panic -> error. `new()` already returns Result; the design kept ConfigError
     empty and panicked. Replaced with `ConfigError::UnknownFlashChip`. Repo
     guidelines say "prefer a fallible API over panics".

  e) Missing `apply_config`. Guidelines require it; ~20 esp-hal drivers have it.
     The one config field is a software policy, so it is meaningful here.

  f) `#[ram]` scoping. FINAL RULE (Scott, 3 Aug): scoped by *flash capability*,
     not by the cache-off window. Every method that performs or could perform a
     flash operation carries it, plus everything on that path. NOT on `new`,
     `apply_config`, `capacity` (reads back the detected value; esp-storage's is a
     field read) or `chip_info`. `new` is on the line because detection calls the
     ROM refresh, which issues a flash command - that refresh sits behind a
     `#[ram]` helper so `new` stays out of RAM, and the linked-section check
     catches it if the compiler inlines the refresh upward.
     I first went too far the other way (guard + ROM wrappers only). That is
     unpoliceable: inlining can move a flash operation into a caller reasoned to
     be safe, and the failure mode is a hang, not a failed assertion. Prefer
     over-applying. See design A18.

  f2) Cache handling is a DELIBERATE CHANGE, not preserved behaviour. Scott
     challenged this and was right that the doc framed it wrongly. Verified from
     ROM disassembly: ESP32 `SPIWrite`/`SPIRead`/`SPIEraseSector`/`SPIEraseBlock`
     call only `SPI_page_program`/`SPI_write_enable`/`Wait_SPI_Idle`; C6
     `_esp_rom_spiflash_{write,read,erase_sector}` call only SPI primitives and
     bit-length setters; the ESP32 patch source's only cache-named functions
     (`spi_cache_mode_switch`, `esp_rom_opiflash_cache_mode_config`) configure
     SPI0 read mode and dummy cycles, NOT invalidation. So the ROM does nothing
     and the driver must.
     esp-storage does nothing either for plain ops - it only invalidates after
     encrypted writes (hardware.rs:37-40) and never suspends the cache. So this
     is us following ESP-IDF. Justification: without invalidation, a write/erase
     to a cache-mapped region can be followed by a cache read returning
     pre-write data; esp-storage escapes it because storage partitions aren't
     normally XIP-mapped, so the gap is latent. See design "Cache handling is the
     driver's job". Revisit if the guard dominates PR A latency numbers.

  g) Encrypted-write 16 vs 32 byte alignment was filed as a test task. It was a
     decision - settled as D2, see section 4.

  h) Derive sets. Config was missing Hash/Default/defmt::Format vs the
     `spi::master::Config` precedent. Error/ConfigError need Display +
     core::error::Error. Flash and ChipInfo need Debug.

  i) `rom_spiflash_legacy_data` is a POINTER on the 8 non-ESP32/S2 targets, not
     the struct. IDF does `rom_spiflash_legacy_data->chip.device_id`. The
     accessor needs an extra indirection there. Was not mentioned.

  j) `esp-hal/src/psram/esp32.rs` already declares `g_rom_flashchip` privately
     (line 265) and reads `device_id` (line 1176). Was missing from the plan's
     file inventory; should move onto the new shared accessor.

  k) `unstable_driver!` compiles the module out entirely without the feature, so
     PR F is a code move (into a plain `#[cfg(flash_driver_supported)] pub mod
     flash;`), not an attribute removal.

  l) FLASH-DEFERRED.md said `common_command` is absent on ESP32/S2/P4. True for
     `spi_flash_hal_common_command` (7 targets) but there is a second, older
     `SPI_Common_Command` / `esp_rom_spiflash_common_cmd` exported on NINE
     targets including S2 and P4. Wider target set than recorded.

  m) FLASH singleton exclusivity. Both drivers consume `peripherals.FLASH`
     (esp-storage re-exports it at common.rs:6, takes it by value at
     common.rs:92), so a binary holds one or the other. Confirmed intended - it
     is what stops two drivers racing one chip - but it means migration is per
     binary, not per call site, and a dependency still on esp-storage blocks the
     switch. This was the ONE item that had been missed until the 4 Aug audit.
     Now in the design as "Migration is per binary, not incremental" and in the
     plan's migration-notes list.

  n) AutoPark on reads. See section 4a - I was wrong, the design was right.


2. ROM DETECTION - THE KEY FINDING (Scott was right)
----------------------------------------------------

Method: disassembled the ROM ELFs. Local set is
`~/.espressif/tools/esp-rom-elfs/20241011`; also downloaded release 20260528 from
github.com/espressif/esp-rom-elfs (contains a C61 ROM the local set lacks).
Tools: `llvm-objdump` for RISC-V; xtensa-esp32-elf-objdump for Xtensa
(llvm-objdump silently produces NOTHING for Xtensa - that caused a false
"NONE-FOUND" on S2/S3 on my first pass).

FINDING: the first-stage ROM bootloader DOES detect the flash ID on 10 of 11
chips (ESP32-S31 was added upstream on 4 Aug; it fits the pattern). `ets_run_flash_bootloader` calls the ROM's own
`esp_rom_spi_flash_update_id`. ESP32 is the sole exception (rev0 and rev300). The
second-stage bootloader repeats the work defensively.

Verified matrix (all revisions in release 20260528, 17 ELFs, all 11 chips):

  chip       revisions checked     ld symbol    impl                     caller
  ---------- -------------------- ------------ ------------------------ ------------------------
  esp32      rev0, rev300         ABSENT       ABSENT                   n/a
  esp32s2    rev0                 0x40016e44   0x40016e44               ets_run_flash_bootloader
                                                                        + ets_unpack_flash_code_legacy
  esp32s3    rev0                 0x40000a8c   0x4004a61c               ets_run_flash_bootloader
  esp32c2    rev100, rev200       0x40000160   0x4005adda/0x4006230c    ditto
  esp32c3    rev0, rev101, rev3   0x4000014c   0x4004d260/0x4004f5ee/0x4004db12  ditto
  esp32c5    rev0, rev100         0x40000184   0x40027c1c/0x400296f0    ditto
  esp32c61   rev100               0x40000184   0x40027ecc               ditto

  esp32c6    rev0                 0x40000174   0x40024b36               ditto
  esp32h2    rev0                 0x4000016c   0x4000d626               ditto
  esp32p4    rev0, rev300         0x4fc0017c   0x4fc0f000/0x4fc0fc46    ditto

Every `esp-rom-sys/ld/*` address matches the ROM ELF exactly. Except on S2, the ld
address is the `__call_esp_rom_spi_flash_update_id` thunk in the ROM's fixed jump
table, which is why it is stable across revisions while the implementation moves.
=> Calling it needs a BINDING in esp-rom-sys, no linker work.

C6 body at 0x40024b36:
    lw   a3, rom_spiflash_legacy_data
    sw   zero, 0x58(SPI1)          # clear W0
    sw   0x10000000, 0x0(SPI1)     # SPI_CMD bit 28 = FLASH_RDID
    lw   a4, 0x0(SPI1); bnez       # poll
    lw   a5, 0x58(SPI1)            # read 24-bit response
    ... byte swap ...
    sw   a5, 0x0(a3)               # store device_id
It also branches on dummy_len_plus[1] for the high-speed/octal case, which a
hand-rolled register read would have to replicate. This is why calling the ROM
function beats copying esp-storage's register poke.

THE ROM'S STATIC DEFAULT IS A TRAP. All 17 ROM ELFs ship `.data_spi_flash`
containing:
    ef401500 00002000 00000100 00100000 00010000 ffff0000
= esp_rom_spiflash_chip_t pre-initialised to a Winbond W25Q16:
    device_id 0x001540EF, chip_size 2 MiB, block 64 KiB, sector 4096, page 256,
    status_mask 0xFFFF
On ESP32 the symbol at g_rom_flashchip's address (0x3ffae270) is literally named
`spi_w25q16`. So an un-detected cache reads as a REAL CHIP AT 2 MiB - no
all-zero/all-ones sentinel catches it. Detection must reject 0x001540EF
explicitly. (It happens to fail the density check anyway, because the static
default is stored in raw order while every runtime writer stores
manufacturer-first, but that is an accident, not a designed safety property.)

Nothing else in any ROM writes the field: the only ROM caller of
`esp_rom_spiflash_config_param` / `SPIParamCfg` is `FlashDwnLdParamCfgMsgProc`,
the serial download-mode message handler, which takes values from the host packet.
On ESP32 every other reference to `spi_w25q16` is a read (nearby stores go to the
stack or the SPI register base; SPIRead reads offset 4 for its bounds check).

ESP32 OPTIONS (all checked, all closed except the bootloader):
  - ROM esp_rom_spi_flash_update_id : absent, rev0 and rev300
  - libesp_rom.a patch library      : NO read-ID function. IDF's
                                      components/esp_rom/patches/esp_rom_spiflash.c
                                      has zero RDID/0x9F references. The patch fixes
                                      read/write/erase/unlock/encrypted-write;
                                      identification was never in it.
                                      (This was Scott's suggestion - it does not work.)
  - esp_rom_spiflash_read_user_cmd  : exists (SPI_user_command_read @ 0x400621b0) but
                                      the ROM writes immediate 7 to SPI_MISO_DLEN =
                                      8 bits = ONE byte. Cannot carry the density
                                      byte. Verified from machine code.
  - ROM SPI_Common_Command          : present at 0x4006246c on rev0 AND rev300, but
                                      NOT exported by esp-rom-sys/ld/esp32/. Exported
                                      on the other 9. Preferred escalation if ever
                                      needed - stays within A1. Argument shape not
                                      reverse-engineered.
  - second-stage bootloader         : always present for espflash-flashed images
  - hand-rolled SPI1 RDID           : flash_rdid bit exists in the ESP32 register
                                      block, but esp-storage avoids it on ESP32 and
                                      it breaches A1

DECISION (Scott, 3 Aug): ESP32 requires an ESP-IDF-compatible second-stage
bootloader. Document it in the module Limitations block and on `new()`; do not add
a chip-specific detection path. Old chip, unlikely to get new bootloaders.


3. BYTE ORDER - CONFIRMED FOUR WAYS
-----------------------------------

Cached `device_id`: manufacturer bits 23:16, memory type bits 15:8, density 7:0.

  1. C6 ROM machine code computes (byte0<<16)|(byte1<<8)|byte2 from the raw
     response, byte0 being the manufacturer.
  2. IDF bootloader_read_flash_id() (bootloader_flash.c:680-685) applies the
     identical ((id & 0xff) << 16) | ((id >> 16) & 0xff) | (id & 0xff00).
  3. ROM patch esp_rom_spiflash.c:29 tests ((chip->device_id >> 16) & 0xff) == 0x9D
     for ISSI.
  4. In-tree: esp-hal/src/psram/esp32.rs:227 FLASH_ID_GD25LQ32C = 0xC86016, with
     GigaDevice's 0xC8 in the top byte, compared against g_rom_flashchip.device_id.

esptool (cmds.py:342-353 @ 8363cae8) and esp-storage (hardware.rs:80-93) instead
take vendor_id = flash_id & 0xFF and size_id = flash_id >> 16, i.e. the RAW order:

  field                       raw RDID order   cached device_id order
  --------------------------- ---------------- ----------------------
  manufacturer                bits 7:0         bits 23:16
  density, standard vendors   bits 23:16       bits 7:0
  density, Adesto (0x1F)      bits 12:8        bits 12:8

Only the Adesto middle-byte case is order-independent. esptool also rejects
0xFFFF3F as a no-response value (cmds.py:1128) alongside 0x000000 / 0xFFFFFF.

HIL consequence: assert decoded capacity against each board's KNOWN capacity. An
"it decoded successfully" assertion passes with the bytes reversed.


4. THE 5 DECISIONS - ALL ANSWERED (Scott, 4 Aug)
-----------------------------------------------

  D1 chunk limit     -> (b) ESP-IDF ceilings: 16384 read / 8192 write.
                        WENT AGAINST my 4096 recommendation. Consequence: the
                        interrupts-off/cache-off window is 2-4x esp-storage's on
                        the direct path, so PR A must measure worst-case INTERRUPT
                        LATENCY as well as throughput. Gate 15 updated.
  D2 encrypted align -> (a) uniform 16 bytes, implement ESP-IDF's ESP32 pre/post
                        decrypted read-back. Rejected: per-chip constant (would
                        leak a cfg into the OTA path). Evidence
                        esp_flash_api.c:1216-1330 (v5.3.1).
  D3 PR F scope      -> (a) inherent methods only; trait impls stay unstable until
                        embedded-storage 1.0. esp-hal ships embedded-hal 1.0
                        unconditionally with stable impls, but EVERY pre-1.0 trait
                        crate is suffixed + optional + behind `unstable`
                        (embedded-io 0.6 AND 0.7, rand_core 0.6/0.9/0.10,
                        embedded-can, nb) and nothing pre-1.0 has ever been
                        stabilized. So PR F de-unstables read/write/erase/capacity
                        only, and the bootloader stays an unstable consumer via the
                        encrypted API regardless.
  D4 D1 seam         -> (a) FlashRegion stays non-generic; private internal
                        abstraction + cfg(test) mock. Generic would break Ota,
                        OtaUpdater, next_partition on a published crate.
  D5 deprecation     -> (a) docs only, no #[deprecated] until there is a stable
                        migration target.

Q1 ("detection fallback") dissolved earlier: call the ROM refresh function; ESP32
documents the bootloader requirement.

Nothing is blocked on a decision. What remains is measurement + implementation.


4a. AUTOPARK ON READS - I WAS WRONG, THE DESIGN WAS RIGHT (4 Aug)
----------------------------------------------------------------

Scott asked why reads park, whether IDF does it, and whether esp-storage has a bug.
I initially argued the design overstated it and that SPI0/SPI1 hardware arbitration
made unparked reads safe. THAT WAS WRONG.

Espressif documents the opposite, in
docs/en/api-reference/peripherals/spi_flash/spi_flash_concurrency.rst (v5.3.1):
  - the SPI0/1 constraint covers "any operations like read/write/erase";
  - "these caches must be disabled while reading/writing/erasing";
  - while disabled, "all CPUs should always execute code and access data from
    internal RAM";
  - hardware arbitration is promised ONLY under CONFIG_SPI_FLASH_AUTO_SUSPEND
    (needs SOC_SPI_MEM_SUPPORT_AUTO_SUSPEND + a suspend-capable flash part, off by
    default). Other escapes: CONFIG_SPIRAM_XIP_FROM_PSRAM,
    CONFIG_APP_BUILD_TYPE_RAM - both mean nothing is fetching from flash.
index.rst:246-251 gives the dual-core mechanism: esp_ipc_call runs
spi_flash_op_block_func on the other CPU to disable its cache and set
s_flash_op_can_start before the caller proceeds.
Also verified in source: esp_flash_read wraps every chunk in
rom_spiflash_api_funcs->start/end; spi1_start -> cache_disable() ->
spi_flash_disable_interrupts_caches_and_other_cpu (spi_flash_os_func_app.c:104-126).

=> A4 is RIGHT and reads keep the guard. Recorded as design appendix B7.
=> esp-storage's unguarded reads ARE a latent bug by that documented constraint,
   so the migration note is a fix, not a tax.
=> qa-test/src/bin/multicore_flash.rs does NOT contradict it: it drives cache
   pressure against write_nor ONLY, never a concurrent flash READ, and it excludes
   esp32 + esp32p4 ("TODO: Make esp32 work"). Our dual-core read test is genuinely
   new coverage - try to include ESP32.
=> Cost compounds with D1: a 16384-byte read chunk stalls the other core for a
   16 KiB read. If PR A latency looks bad, turn down the READ CHUNK LIMIT, not the
   guard.
=> The one sanctioned relaxation is flash auto-suspend; filed as deferred sec 10.
